# 记忆折叠与工具结果取回

## 设计目标

会话原文是事实源，发送给大模型的内容是可压缩的推理视图。折叠只改变内存副本，不修改 MySQL 中的 `chat_message`，因此既能控制上下文长度，也能在需要时恢复完整工具结果。

## 数据分层

| 层级 | 内容 | 用途 |
| --- | --- | --- |
| 原始记录 | user、assistant、tool 消息和工具元数据 | 审计、恢复、日志追踪 |
| 推理上下文 | 经过多级 fold 的消息副本 | 控制模型输入规模 |
| 滚动摘要 | 目标、约束、实体、待办、已完成事项 | 跨轮次恢复语义状态 |
| 长期记忆 | 已审核 Case 的业务规则和处理方案 | 按 Agent 跨会话召回 |

## 每次推理前的处理顺序

```text
MySQL chat_message
    -> HistoryMessageMapper
    -> sanitize（校验 assistant.tool_calls 与 tool 回执）
    -> 轮内折叠（保留近期步骤，压缩旧工具结果）
    -> 轮间剥离（旧轮次保留用户需求和最终答复）
    -> 单条消息截断（保留 JSON 结构和关键错误）
    -> 最终上下文预算裁剪
    -> sanitize
    -> Spring AI Prompt
```

默认折叠策略为：最近 6 个工具步骤完整保留；更早步骤清空冗长参数并压缩工具结果；更早的步骤生成结构化步骤摘要。历史上下文超过 40,000/80,000 字符时逐级剥离，单条消息超过 20,000 字符时折叠，最终由模型上下文预算做安全裁剪。

## 工具结果指针

折叠后的工具结果不会只写“内容已省略”，而是保留稳定坐标：

```text
[tool-result-folded]
tool=query_feedback
retrieve via retrieve_tool_call("call_feedback")
```

指针中的 `tool_call_id` 来自平台持久化记录，不由大模型生成。错误首行、关键路径和工具名称也会保留，便于模型继续判断。

## 取回闭环

模型需要完整内容时调用 `retrieve_tool_call(toolCallId)`。工具从当前 ReAct 会话获取 `sessionId`，按 `sessionId + toolCallId` 查询原始工具交换记录，返回工具名称、原始参数、结果内容、截断标记和原始长度。这个过程只读取历史记录，不重新执行 MCP、文件或命令工具。

```text
折叠指针
    -> retrieve_tool_call(call_feedback)
    -> 会话级 MySQL 查询
    -> 完整工具结果
    -> 当前 ReAct 轮次继续推理
```

## 不变量

- 数据库原文永不因 fold 被覆盖或删除。
- 每一级折叠前后都执行消息配对校验。
- 当前用户轮次不删除。
- `assistant.tool_calls` 与 `tool` 回执不能被拆开。
- 工具取回失败时返回明确错误，不自动重跑原工具。
- 滚动摘要通过消息覆盖游标增量生成，并在事务内更新摘要和结构化状态。

## 动态预算与 ReAct 回合闭环

固定的 8000/16000 只适合作为旧版本默认值，不代表每个模型的真实窗口。运行时按
`模型上下文窗口 - 最大输出预留 - 安全边界`计算有效输入预算，再用 60% 作为摘要软阈值、
85% 作为强折叠阈值；模型未配置窗口时使用 32K 的安全默认值。系统提示词、MCP/内置工具描述
和消息正文都会计入本次估算。

ReAct 不是只在入口折叠一次：每次模型准备下一轮调用时，都把当前回合的 assistant
`tool_calls` 和工具响应重新组装成 Map，重新计算预算并执行折叠。折叠只改发送副本，原始消息仍写入
MySQL。模型返回工具调用前先保存 assistant 的 `tool_calls_json`，工具执行完成后再保存同一
`tool_call_id` 的 tool 行，因此审计和取回可以关联两侧。

取回工具是 ReAct 的内部只读能力，不需要业务人员重复勾选。首段取回超过 20000 字符时返回
`hasMore`、`nextOffset` 和 `originalChars`，模型可调用分页接口继续读取；取回只查询当前会话已保存
的结果，不会再次执行 MCP、文件或命令工具。

滚动摘要采用三段式流程：先读消息和当前摘要游标形成快照，再在事务外调用模型生成 JSON，最后由
短事务校验“最新消息 ID + 旧摘要版本”未变化后写入摘要和状态。并发期间游标变化时丢弃本次旧结果，
由下一次异步 worker 重新计算，避免长时间占用数据库连接和覆盖新消息。
