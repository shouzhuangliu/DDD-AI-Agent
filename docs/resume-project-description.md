# 简历项目描述：AI Agent 反馈与 Case 运营平台

## 推荐项目名称

**企业级 AI Agent 反馈与 Case 运营平台**

## 一句话定位

面向企业用户反馈和运维问题的 AI Agent 运营平台，将对话、反馈、案例提取、人工审核、问题跟踪和 Agent 长期画像串成闭环。

## 简历精简版

### 企业级 AI Agent 反馈与 Case 运营平台

**项目周期：** 2025.12 - 2026.02

**技术栈：** Java 21、Spring Boot、Spring AI、MySQL、MyBatis、PostgreSQL、pgvector、Vue 3、MCP、SSE

**项目描述：**

面向企业用户反馈和运维问题处理的 AI Agent 运营平台。系统支持 Agent 配置、模型切换、ReAct 对话、工具调用、反馈采集、AI Signal/Case 提取、人工审核和 Agent 长期画像沉淀，解决 AI 对话结果难追踪、问题无法形成案例资产以及工具能力缺少治理的问题。

**个人负责与核心实现：**

- 设计反馈到 Case 的业务闭环：对话消息和用户反馈进入异步分析队列，经分类、证据关联、加权评分后生成候选 Case，再由管理人员进行确认、处理、解决、归档或回退。
- 实现按 Agent 隔离的 Case 工作台，支持负责人、处理状态、解决方案、审核记录、证据链和 Agent 画像展示，避免不同 Agent 的问题数据相互污染。
- 重构 ReAct 执行引擎：由应用层持有模型调用和工具循环，支持工具白名单、30 步上限、执行状态持久化、SSE 过程事件、失败处理以及用户取消。
- 实现一级 Subagent 委派机制：通过 `dispatch_subagents` 批量提交相互独立的任务，服务端使用调度线程池和执行线程池并行处理，最多 3 个子 Agent，并支持超时、取消、失败隔离和结果汇总。
- 建立 MCP/Skill 能力治理流程：支持注册、连通性检查、工具发现、安全扫描、沙箱测试、审核、发布和 Agent 绑定；Skill 通过工作目录隔离并使用 `read_file` 按需渐进式加载，避免一次性污染上下文。
- 实现模型配置和运行时装配：模型、接口地址和凭证引用存储在数据库，对话过程中可按会话选择模型；应用启动时校验并装配模型 Bean，区分 MySQL 业务数据和 PostgreSQL/pgvector 长期记忆数据源。
- 使用 Vue 3 实现 Agent 对话、会话历史、模型切换、反馈、Case 工作台、MCP/Skill 管理和执行过程展示，并通过 SSE 实时显示工具、Todo、Subagent 和执行状态。

## 面试重点版

### 1. 最值得讲的业务闭环

用户反馈不是直接写入长期记忆，而是经过：

```text
对话消息
  -> 显式反馈 / AI Signal
  -> 候选 Case
  -> 证据与评分
  -> 人工审核
  -> 处理中
  -> 已解决 / 归档
  -> Agent 长期画像
```

这个设计重点解决了两个问题：

1. AI 识别出的“可能问题”不能直接污染业务知识库。
2. 每个案例都有来源消息、处理状态、负责人和解决结果，可以追踪和复盘。

### 2. 最值得讲的技术难点

**ReAct 与 Subagent 执行控制：**

- 主 Agent 由 Java 服务端显式控制模型轮次和工具结果拼接。
- Subagent 使用独立上下文，不直接写主会话消息。
- 并发上限由服务端信号量强制控制，不依赖模型提示词。
- 主 Agent 取消会传递到子 Agent，子 Agent 在当前模型调用或工具边界结束后停止。
- 通过 `executionId`、`taskId` 和状态表追踪执行过程。

**能力治理与安全边界：**

- Agent 只能调用绑定且通过白名单授权的工具。
- Skill 上传先校验压缩包路径、文件数量和危险内容，再进入沙箱测试和发布流程。
- Agent 工作目录按 Agent 隔离，文件读写和命令执行不能越出工作目录。
- MCP 发布和 Agent 绑定分离，发布只代表能力可用，是否使用由 Agent 配置决定。

**双数据源设计：**

- MySQL：Agent、会话、消息、反馈、Case、审核、执行日志等业务数据。
- PostgreSQL/pgvector：长期记忆向量及其 Agent/Case 元数据。
- 通过显式 DataSource 和 Bean 限定，避免 PostgreSQL 向量 SQL 被错误发送到 MySQL。

## 旧版描述建议删除或改写

### 不建议继续使用

- “高可用”：当前项目没有足够的集群、故障转移和压测证据，不建议写。
- “基于 4 步执行流程”：现在项目重点已转为反馈、Case 和运营闭环，旧的四角色流程容易让面试官误判项目重点。
- “接入 Elasticsearch、百度搜索、Filesystem 等多个真实 MCP”：只有确实部署并验证过的外部服务才写具体名称，否则改成“MCP 工具接入与生命周期治理”。
- “RAG 知识库”：当前更准确的说法是“基于 pgvector 的 Agent 长期记忆和相似检索”。
- “零代码热插拔”：改成“配置驱动的 Agent 能力装配和运行时模型注册”，更准确也更容易解释。

## 30 秒项目介绍

这是一个面向企业反馈和运维问题的 AI Agent 运营平台。用户可以进入指定 Agent 对话，Agent 根据绑定的 Skill、MCP 和工具完成问题分析。系统会把用户反馈异步提取成 Signal 和候选 Case，保留原始对话证据并交给管理人员审核，处理完成后再沉淀为该 Agent 的长期画像。技术上我重点实现了 ReAct 工具循环、一级 Subagent 并行委派、SSE 执行过程、Skill/MCP 安全发布链路以及 MySQL 与 pgvector 的双数据源隔离。
